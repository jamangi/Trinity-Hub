# Trinity Hub project guidance

- Work only in Trinity Hub. The sibling Server Repair repository is a read-only story reference; do not modify it or carry its game implementation tasks into this project.
- Use fictional identities. Never add the real employer's name, identity mappings, identifiable employee details, credentials, network addresses, unit identifiers, or raw internal work records. Use synthetic examples in committed artifacts.
- The root README holds purpose and durable strategy. Keep mutable environment details in `context/` and tool proposals in `buildorders/`.
- Distinguish user-reported observations, locally confirmed facts, general technical references, proposals, and unknowns. Do not turn story lore or AI guesses into operational facts.
- Preserve unknown alias bodies, error meanings, thresholds, and test-stage semantics as unknown until supplied. Do not invent executable repair instructions.
- Start with personal usefulness, minimal access, voluntary adoption, and credit to contributors. Record maintenance cost and a stop condition for each tool.
- Read the relevant build order and context before implementing it. Planning approval does not establish workplace system access or authorize running commands on units.
- Keep knowledge separate from presentation so a personal index can later support a wiki and decision aid. Add platforms and dependencies only when a concrete need supports them.
- For documentation changes, check local Markdown links, whitespace errors, factual status labels, and fictional naming. For code changes, also run checks appropriate to the implementation. Report changed files, verification results, and remaining dependencies.
